# ATME production audit and live-test plan

12 November 2026. Scope includes the Windows Studio, local HTTP and MCP services, SQLite projects, media and timing, renderer, export, packaging, source recovery and user-visible delivery. The baseline is the integrated source at `f3a759a1`. The installed September application, the source checkout and a newly built installer are separate deliverables.

## Where the production path broke

The apparent loop had multiple causes. Historical verification repeatedly exercised renderer internals while the public project dispatcher still rejected v2 layouts. The interrupted full run produced no terminal result. Independently, a worker that terminated after recording a running status could leave the Studio waiting forever. Only the last of these requires recovering an individual project job. Render progress and software-development progress should be measured separately.

## Completion plan

1. **Secure the work.** Restore the GitHub source snapshot into an independent checkout. Compare required code, contracts, fonts, artwork, lockfiles and tests. Preserve private working history separately and list every exclusion.
2. **Make one saved revision authoritative.** Exercise two clients, late Studio responses, changes to timeline selection and output profile. Success means the exact reviewed text, placed recording, canvas and source revision reach the exported file.
3. **Make interrupted work actionable.** Verify a real process exit releases its claim, a second client cannot duplicate a live job, a failed launch is visible and an explicit retry completes. Use a named check with a terminal result for each defect.
4. **Deliver through the public entry points.** Create and reopen a project, author through MCP, prepare speech timing, preview saved artwork, render both orientations, decode the MP4 and verify its recorded hash. For supported v2 work, verify the MP4 actually contains the authored pixels. Record any unsupported combination at validation.
5. **Deliver the Windows candidate.** Build from the integrated source, verify encoder and model dependencies, then run the packaged HTTP/stdio and Studio against disposable data. Save the installer digest and repeatable live-test instructions. Preserve the existing installation and projects.
6. **Decide launch scope from evidence.** Exercise an operator-selected original recording with the intended connected AI. Review the exported movie in a player. Resolve each outstanding delivery or creative-quality failure against that saved revision. An installer tested on a second Windows machine establishes fresh-install behavior beyond the development host.

No project-wide rewrite is needed. The work to start afresh is the release artifact, its reproducible verification and a current release record. Keep the stored projects, original media, renderer/compiler, asset catalog, editor and project APIs. Historical phase documents remain development history.

## Live operator test

1. Start the candidate with a separate project directory for the first run. Open a project and choose **Help → Speech timing model**. Prepare the English model. On a new machine the first preparation needs access to the model weights. Subsequent timing can use the local copy.
2. Open **AI Connection** and copy the configuration for the intended client. After connecting, confirm the Studio indicates an active session. Create a project and upload the recording. Place the intended media on the timeline.
3. Ask the connected AI to read the project state and capabilities, submit the script or recording-derived scene structure, prepare timing, and author the storyboard and layout for the selected profile. For a script-led project, read the displayed script and approve that revision in Studio.
4. Review the storyboard and seek the preview. Open **Export Check**, resolve any listed issues, then select **Render**. A successful run appears under **Renders**. Open it and choose **Save MP4**. Manual timeline export is available for a video edit that has no authored animation.
5. Play the saved file in an independent player and check intelligibility, timing, framing and artwork. Close and reopen the same project and retrieve the same completed run. Test a second orientation with a layout authored for its canvas.

## Backing up an actual production project

GitHub holds the software. Studio project records, recordings, assets and rendered movies live in the configured ATME data directory. To take a consistent offline copy, close Studio and its connected MCP clients after running jobs finish, then copy the entire directory. Restore that directory to a separate location and launch the candidate with its absolute path in `ATME_DATA_DIR`. Keeping the database together with its media and SQLite journal files preserves references and recently committed changes.

## Findings closed during this audit

| What was wrong | Change and verification |
| --- | --- |
| A worker could disappear and leave a revision permanently queued. An MCP recording-led export also hit a database lock before encoding. | Each admitted job holds an OS-released SQLite lock and writes its terminal result independently of the client. A completion receipt recovers a finished result if SQLite is temporarily busy. Local Windows project databases use WAL so readers can see committed work during writes. Interrupted timing and render jobs, concurrent requests, client disconnect, rollback and receipt recovery were exercised. The same failed recording-led project completed at revision 4 and reopened through a fresh MCP connection. |
| A supporting import could displace the timeline's narration. Concurrent edits could produce a mixed-revision snapshot. Switching profiles could reuse a cached video with the wrong canvas. | The timeline now determines authority, snapshots check their revision after preparation, and derived video caches include dimensions and frame rate. A real manual export converted an unedited source to MP4 in each orientation. Two concurrent cache writers left one complete file. |
| Camera composition could replace mastered audio, drop its tail or produce extra video frames. | Assembly now derives its video frame budget from the PCM sample count and hashes the final movie. Ten media-boundary tests include shorter and longer graphics tracks, exact passthrough and checkpoint invalidation. A 7.011-second master kept all AAC packets and all 211 required frames. |
| Stored v2 projects could pass internal renderer tests while the public export route rejected them. A client also lacked a normal way to obtain compilation inputs. | MCP now exposes the stored source, profile, revisions and canonical hashes needed for authoring. A real stdio client submitted a plan and layout, obtained the compilation context, rejected a stale draft and requested a genuine preview. The export uses authenticated frozen assets and the same compositor as preview. Two 300-frame movies verified landscape sound cues, scoped silence, portrait camera compositing, decoded frames, AAC and manifest hashes. |
| The production export repeatedly validated the same typed layout and resolved timeline while rendering adjacent frames. | A batch now prepares immutable inputs once. Across 35 frame comparisons, old and prepared paths produced matching hashes. On the shared build machine the 16-frame portrait comparison improved from 22.44 to 9.66 seconds. The landscape comparison went from 7.05 to 9.30 seconds. These samples establish frame parity and removal of repeated validation. They do not establish a general throughput gain. |
| Studio could paint a stale preview, approve a script from the wrong view, hide a saved storyboard or buffer an entire exported movie in memory. | Studio pins artifact reads and approvals to the displayed revision, ignores stale responses and streams a completed movie to the player or download. The Windows WebView opened a saved project, saved its 74,944-byte portrait movie, matched its SHA-256, created a new project and displayed the missing inputs in Export Check. |
| Studio overlooked v2 board activations and a legacy preview could stop at the last illustration while narration continued. | Studio reads each stored layout format, and the attached narration supplies the duration when there are no clips on the source timeline. The public preview served a frame at 5.5 seconds after the last board of a seven-second recording and rejected a seek past the recording. A layout-only draft remained previewable. |
| A packaged engine could miss native FFmpeg or speech-model resources and appear dead while loading before the HTTP server bound. | The frozen runtime uses the actual encoder, includes the speech detector and avoids unnecessary DSP imports during server startup. One measured healthy cold launch took 63.05 seconds, beyond the old 60-second desktop deadline. Studio now allows three minutes and shows the engine error. Server binding is restricted to loopback. |

The 50-check production subset initially had 48 passes. One new assertion looked in the wrong field for the uploaded media revision. The other failure revealed the audio/frame truncation above. Both were corrected and checked directly. The focused verification also includes 11 corrected workflow checks, 11 storage/recovery checks, 18 sound/MCP checks and seven listener checks. These groups overlap. Adding the counts would overstate coverage.

The runtime revision was restored from GitHub with all 570 published tree entries matching. [Runtime source checkpoint](https://github.com/Bukassi600104/ATME/commit/7d7d0a70b8eca6b15ef01bc7920d10fba917c083)

The frozen Windows engine rendered and reopened two spoken projects in 1280×720 and 720×1280. A camera export produced all 179 frames for its 143,136-sample narration master, with byte-identical encoded AAC packets. Packaged scored and portrait-camera v2 exports matched their sampled preview pixels and expected mixed or mastered AAC. An independent stdio session also verified that replacing the plan or changing the canvas invalidates the earlier compilation inputs.

## Remaining work, by intended release scope

- **Immediate live test.** Use the included test material once to establish the local setup, then use an original narration and brief with the intended AI client. The automated speech sample uses a synthesized voice, local acoustic recognition and real codecs. Only the operator can judge editorial accuracy, pacing and suitability for publication.
- **Automatic v2 directing.** The connected producer currently authors the visual plan, layout and resolved sequence. The public compilation context supplies the pins and fingerprint. A general director that turns arbitrary prose or a bare storyboard into that sequence is a separate capability. It needs an explicit input grammar, trigger resolution against measured speech, diagnostics for ambiguous cues and examples verified through the public render path.
- **Long-form throughput.** Benchmark a representative ten-minute authored project on target hardware with competing build processes closed. Record cold startup, preparation, frame rate, peak memory, disk use and final file duration. The ten-second v2 fixtures establish functional output but cannot support a long-form speed promise. The first measurements attributed roughly 273–281 seconds to rendering 300 frames and about three seconds to muxing on the shared build machine.
- **Editorial monitoring.** Studio previews visuals and source audio. The completed MP4 and render player contain the authored editorial mix. Auditioning those sound buses live before export would require a synchronized audio-preview path.
- **Distribution.** Rehearse a clean install, upgrade with retained projects, uninstall and restore on a second Windows machine. Exercise the connected client chosen for launch. The current host has an existing ATME installation and no Windows Sandbox executable. Verify distribution signing and release notes before advertising a public general-availability release.
